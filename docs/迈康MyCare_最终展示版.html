1 项目定位与要解决的问题

一句话定位：为老年慢病患者提供一个「能记录、能判定、能解释、能被医生调整」的日常健康管理工具。系统的核心不是"AI 聊天"，而是把医学判定交给确定性规则、把表达交给模型。

要解决的核心问题

问题本系统的应对
老人看不懂指标数字用「提示 / 关注 / 预警 / 紧急」四级产品词表表达，配可执行动作，不用「高危 / 中危」等专业分层术语
AI 直接给医学结论不可信规则判定完全由 clinicalRules.js 计算，模型只负责把结果转成自然语言，不得自定阈值或等级
一天多次测量容易被"覆盖"事实层「一次测量一条、纯追加、永不覆盖」，作废只打 record_status='void'
AI 建议没人把关患者对话产生的任务调整一律进入 pending，医生审结后才生效
AI 评分不可解释评分分两层：规则分（官方）、AI 辅助分（仅同屏参考，不参与任何分级）；模型只提意见，不是分数、不构成一层
设计主线：事实层与规则层分离 —— 数据只描述「发生了什么」，规则只回答「这意味着什么」，模型只负责「怎么说给人听」。

3 注册用户从 0 到 1：数据落在哪里

5 智能体应用地图：谁在什么位置、用了哪些指标

前面说明了「有哪些智能体」。这一节回答三个具体问题：它们分别出现在页面的哪个位置、每个位置能拿到哪些数据、以及「今日任务」与「健康评分」这两条主线究竟是怎么被它们串起来的。

一句话总纲：智能体不是「到处插一个聊天框」，而是落在 6 个位置、扮演 6 种不同角色。每个位置能读到什么、能产出什么、能不能写库，都由接口契约事先规定死 —— 位置不同，权限不同，这正是「同一个模型在不同地方行为可控」的原因。

5.3 AI 参与评分：到底用了哪些数据指标

评分分三层，只有第一层是分数，第二层是「意见」，第三层只是一个同屏参考值。三层共用同一份输入快照 buildScoreSnapshot()，因此三边永远不会互相矛盾。

L1 · 规则分（Rule Score）—— 唯一官方分，纯确定性

四个维度，权重合计 100；分母 = 该患者「适用维度」的权重之和，由疾病谱决定，不随当日有没有录数据而漂移。

维度权重取数来源适用条件达标判定
步数30daily_health_records.steps恒计（通用项）≥ 10,000 步为满分档
血压25systolic_pressure / diastolic_pressure
兼容层口径：当日收缩压最大那一条		疾病谱含「高血压 / 血压 / 代谢综合征」按个体化目标比值给分
血糖25blood_sugar
兼容层口径：优先空腹值，否则取当日最高		疾病谱含「糖尿病 / 血糖」按个体化目标比值给分
运动20exercise_minutes恒计（通用项）≥ 60 分钟为满分档
未录入 = 记 0 分，并标 status:'missing'，同时保留该维度在分母里。举例：一位高血压患者当日什么也没录 → 分母仍是 30+25+20 = 75，得分 0，档位「需干预」。绝不能因为「今天没数据」就把血压从分母里摘掉 —— 那会让「什么都不做」反而拿到更高的分。

近 7 日记录同上字段的最近 7 行，供模型看趋势
系统已算出的规则分总分、档位、适用分母
规则分分项每维度的 earned / weight 与状态（含「未记录」）
未录入项清单明确列出哪些维度当日没有数据

模型只被要求输出一个 JSON：{"adjustments":[{"dimension":"维度","delta":整数,"reason":"依据"}],"narrative":"…","insights":["…"]}。dimension 的枚举是动态下发的 —— 只给该患者适用的维度，模型连「猜一个不适用的项」的机会都没有。

L3 · AI 辅助分（AI-assisted Score）—— 纯函数合成，只做同屏参考

Σdelta = Σ adjustments[].delta rawAssisted = Rule Score + Σdelta assisted = clamp(rawAssisted, 0, 100)

合成结果必须满足守恒式：assisted − ruleScore === Σdelta。当发生截断时（例如规则分 98、Σdelta 为 +10），页面会如实显示「规则基线 98 · AI 调整 +10 → 原始 108，已截断到 0–100」，绝不静默 —— 否则用户一减就会发现对不上。

六条硬约束：任一不过，整包丢弃

约束取值为什么要有这一条
调整条数上限≤ 4 条防止把一条大意见拆成十条小意见，稀释可读性
单条 delta 区间−5 ~ +5规则分不能被模型「翻盘」，只能在边上微调
Σ|delta| 上限≤ 10防止「每条都在范围内、合起来却很大」
维度不得重复同维度仅 1 条同上，堵住「拆分多条规避 ±5」这条路
维度必须适用枚举内且在适用集不给没有数据的维度凭空加减分
理由长度1 ~ 80 字必须说清依据，不接受空理由凑数
三条不可逾越的红线（与 5.3 的实现一一对应）：
① 模型永远不得输出 0–100 的分数，它只能输出 delta；
② 辅助分绝不参与等级 / 档位 / 达标率 / 落库 —— 那四样只认 clinicalRules.js 与 healthScore.js；
③ 违反约束时整包丢弃、不做部分采纳，并如实告诉用户「AI 建议未通过校验，已忽略」。
「结构性畸形」与「违反约束」为什么要分开报？

两者对用户的含义完全不同：结构性畸形（输出里压根没有 adjustments 数组）= 模型没按格式作答，等价于拿不到意见，界面显示「AI 解读暂不可用」；违反约束（给了意见但不合法）= 要如实告知「已忽略」。

混在一起报会让用户误以为「AI 看过但否决了你」，实际上模型可能什么都没说。四种状态因此严格区分：ok / rejected / unavailable / 未生成（冷缓存返回 null，界面显示「未生成」而不是「不可用」）。

5.4 今日任务联动：它是怎么被串起来的

「今日任务」不是一个数据库表，而是每次请求即时算出来的派生视图。这条链路上有四个环节，每个环节的权限都不一样：

环节谁负责做了什么 / 不能做什么
① 确定性派生
buildDailyTasks()		 输入：日期、疾病谱、主诊断、规则判定结果、当日血压 / 血糖明细、用药计划与打卡、近 7 日计数、个体化目标、当日行为、医生覆盖包。
输出：任务数组（含 target / slots / reason / level）。
不落库 —— 刷新页面就重算，永远与今天的判定一致。
② 主任务由主诊断决定 主诊断含「高血压」→ 生成血压监测；含「糖尿病」→ 生成血糖监测；含「肥胖」→ 生成体重记录。任务域只由诊断派生，任何一方都不许凭空新增一个任务域。
唯一例外：医生审结「新增监测申请」时，可以启用规则库里已经存在的白名单监测域（bp_monitor / bg_monitor）—— 本质是把「该域未被此患者的主诊断派生」变成「已派生」，仍然不是凭空造任务域。
③ 频次由规则等级决定 同一任务域，「正常档」和「升档」对应不同的测量次数与时段（slots）。等级来自 clinicalRules.js 的唯一裁定，模型不得改写。
④ 医生覆盖层
prescriptions.target_goals		 医生审结后写入，buildDailyTasks({ taskOverrides, addedTasks }) 在派生末尾套用。改参数时只能动 target / slots / enabled；新增监测项时只能启用白名单内的监测域（addedTasks，当前白名单恰好两项）。两条路径都不得新建规则库外的任务域、不得改医学阈值。这是任务相关唯一的写库出口，且只有医生审结会走到这里。

从「患者一句话」到「任务真的变了」——完整闭环

提案类型什么时候产生审结「同意」的语义
参数调整型 患者要求改一个已经存在的任务参数（如「步数降到 3000」） 生成覆盖包写入 prescriptions.target_goals，次日派生即生效；覆盖包 JSON 必带 kind 字段以便被健康建议页正确消费
新增监测申请型 患者要求一个当前未生成的监测项（如「每天测一下血糖」） 同意即启用并计入评分：该监测域立即进入患者今日任务（addedByDoctor = true），并同时计入当日评分的适用维度（分母），医生备注里同时写明「已将该需求记为随访关注项」；返回 tasksUnchanged = false。仍受两条边界约束：只能启用规则库里已存在的白名单域（当前 bp_monitor / bg_monitor），白名单外返回 E_ADDED_TASK_UNKNOWN；该域已被主诊断派生时返回 E_ADDED_TASK_ALREADY_GENERATED，不会误判成「申请新增」。这里不伪造「当前值 → 建议值」；「修改后生效」可由医生指定测量时段，未指定则回落规则库默认时段。
「实际做了多少」为什么必须单独存一个字段？任务卡片上有两个数：done 是封顶后的完成数（用于算完成度），actualCount 是真实测量次数。患者今天量了 6 次血压而上限是 3 次时，进度显示 3/3，但界面要如实写「今天实际测了 6 次」。展示「实际做了多少」一律用 actualCount，不得拿封顶值冒充真实值。

可以做（有代码与验收为证）不可以做
通过工具取数（档案、体征、勋章、预警、知识库）直接读数据库表 —— 只能走工具，工具返回什么它就看到什么
调用确定性函数算趋势、算风险、算规则分自定义阈值、等级、达标率 —— 一律以工具返回值为准，且工具内部就是 clinicalRules.js
把判定结果转述成面向老年人的自然语言直接输出 0–100 的分数（评分接口同理，只能给 delta）

提出任务调整提案（写入 is_active=0 的待审行）绕开医生审结直接改患者任务

读到该患者过往诉求与医生结论（弱记忆：只读、有界、按 patient_id 隔离）自己写记忆 —— 不落库对话正文、不新建记忆表；更不能把历史记录当成现状（要当前值必须调工具）
一句话收口：智能体在本系统里承担的是「取数 → 调确定性函数 → 解释表达 → 提建议（不生效）」这条链，而判定与生效始终握在 clinicalRules.js 与医生手里。这也是「模型可以换、结论不会变」的原因。

5.6 跨会话「弱记忆」：智能体记得什么、不记得什么

先说结论：对话正文不落库。22 张表里没有任何一张是「消息表」—— agent_runs / reminders / vision_records 三张表全项目零写操作（可检索 INSERT INTO / UPDATE / DELETE FROM 自证）。前端 chats 是 React useState 内存态，刷新页面 / 换患者即清空；后端把前端上传的最近 10 条原文拼进 messages，用完即丢 —— 没有会话表，也没有进程内会话 Map。

层数据来源生命周期与边界
本轮对话 前端内存 chats 的最近 10 条，随每次请求上传 刷新页面即失。不落库、不入 localStorage（白名单仅 user / userSettings）
档案驱动的个性化 patients / patient_conditions / patient_lifestyle / patient_targets / badges + 近 7 天记录 每轮按 patient_id 重新装配，是"派生视图"而不是"记忆"。个性化条目由 clinicalRules.js 依据生活画像算出，模型不参与
弱记忆（本版新增） prescriptions 中该患者的提案行（患者原话 + 审结状态）
+ doctor_notes（医生对该患者的最近结论）		 纯读既有表，不新增表、不改 schema；有界回灌进系统提示词

弱记忆的六条边界（逐条可验收）

  • 只读：agentMemory.js 只有 SELECT，零 INSERT / UPDATE / DELETE；读取前后全库 22 张表逐表内容一致。
  • 按 patient_id 取，绝不跨患者：患者不存在 → 抛 E_PATIENT_NOT_FOUND，不回落示范患者。
  • 有界：诉求 ≤ 3 条、结论 ≤ 2 条，单条截断（原话 60 字 / 结论 80 字），提示词块总长 ≤ 1200 字符。
  • 只作历史参考：提示词块显式声明「这不是本次新信息、可能已经过期；凡涉及当前任务 / 数值 / 等级 / 达标率，必须调工具查」。它不参与任何确定性判定 —— 规则引擎的入参里没有 memory。
  • 不含阈值与等级：申请描述刻意不搬运 proposedValue，只记「患者想改什么」；数值判定仍是 clinicalRules.js 的专属职责。
  • 空记忆不注入：无任何记录时返回空串，不往提示词里塞噪声。

实测：同一位患者，跨会话能续上话

患者：咱俩之前是不是聊过我想监测血糖这件事？后来结果怎么样了？ ↓ 系统提示词里被注入的历史上下文（只读、有界） · 过往诉求 2 条（含患者原话与「医生已同意」） · 医生最近结论 1 条（李医生：已通过，空腹 / 餐后 2h，每日 2 次，计入当日评分） ↓ 模型回复 「您提了两次：想每天测一次血糖。李医生已经审结：同意…… 从今天起，您的每日任务里加上了「血糖」这一项：空腹一次、餐后 2 小时一次，每天 2 次。 这项也会算进您当天的健康评分。」 同时它用工具查到当前数据：血糖尚未记录 → 该项 0 分 → 总分 56；今日血压 160/90；步数 8000 关键点：历史（来自弱记忆）与现状（来自工具查询）各归各位，没有互相污染 —— 没有把上次的目标值当成今天的完成值，也没有把"医生已同意"说成"我帮您加上了"。
对外口径：可以声称「智能体能读到该患者过往的诉求与医生结论（只读、有界、按 patient_id 隔离）」；不能声称「智能体有长期对话记忆」或「会自己记住患者说过的话」—— 它不写任何记忆，只是每轮把既有表里的记录重新读一遍。
已知问题（不影响本版功能，如实披露）：两张表的时间基不一致 —— prescriptions.generated_date 由读写方以 new Date().toISOString() 写入（UTC），而 doctor_notes.created_at 走 schema 默认 strftime(…,'localtime')（东八区），同一个审结动作的两条记录实测相差 8 小时。弱记忆因此只渲染日期、不渲染时刻（不做时区换算，避免自行推算时间）。该问题已单独记录，未经本次改动修复。

13 当日健康评分（Rule Score）

src/utils/healthScore.js 的 computeDailyHealthScore() 是唯一的官方分。它按"适用维度归一化"计算：只有与患者疾病谱相关的维度才计入分母。

血糖25疾病谱含「糖尿病 / 血糖」

缺测不得满分：某维度未录入 → 该维度记 0 分，并在 missing[] 中标注。这样"没测"不会被算成"达标"，也不会被算成"没做"而不计入分母 —— 分母固定为适用维度。

14 AI 参与评分：两层评分与六条硬约束

这一节回答一个容易被质疑的问题："AI 会不会乱改分数？" 设计答案是：系统只产出两个分数（规则分 / AI 辅助分），而模型永远无法直接输出分数 —— 它只能提出可解释的调整项。

两层评分与职责（不得混用）

名称是什么权限
规则分
Rule Score		 computeDailyHealthScore() 的确定性结果 唯一官方分 · 界面主数字
AI 辅助分
AI-assisted Score		 composeAssessedScore(rule, adjustments) 的确定性合成结果 仅同屏参考 · 绝不参与预警 / 档位 / 达标率
模型的评估不是一层评分：模型只输出 adjustments[]（每条为「维度 + delta + 理由」），它没有分数形态，只是喂给 AI 辅助分的原料，且必须通过下方六条硬约束校验（任一不满足即整包丢弃）。因此对外统一表述为两层评分——模型的意见只以「理由行」的形式出现在 AI 辅助分里。

六条硬约束（任一不满足 → 整包丢弃，不做部分采纳）

#约束说明
1调整条数 ≤ 4防止刷条数
2dimension ∈ 患者适用维度不给非相关维度提意见（如无糖尿病的患者不给血糖意见）
3不得重复 dimension防止"拆分多条规避 ±5"
4delta 为整数且 |delta| ≤ 5单条调整幅度受限
5reason 去空白后 1–80 字必须给出理由（"不做黑箱"的前提）
6Σ|delta| ≤ 10总调整幅度受限

合成、守恒与 clamp

assisted = clamp(rule + Σdelta, 0, 100) clamped = (assisted !== rawAssisted) 守恒式：assisted − rule === Σdelta ← 仅当 clamped === false 时成立； 被 clamp 时必须如实上报 clamped / rawAssisted，绝不静默

缓存与状态

  • 缓存键 inputHash =（当日体征 + 疾病谱 + Rule Score）的 FNV-1a 32 位稳定哈希。数据一变即失效。刻意不用 node:crypto —— 该模块要同时在浏览器里跑，而它只当缓存键。
  • 只缓存确定性结果（ok / rejected），不缓存 unavailable（瞬时故障；"模型未配置"是零成本布尔复检）。
  • aiStatus 三态：ok / unavailable（未配置 / 调用失败 / 结构畸形）/ rejected（违反约束）。GET 冷缓存返回 aiStatus: null（≠ unavailable，界面据此说"生成中"而非"暂不可用"）。
  • 结构性畸形（structural: true）与违反约束（rejected[]）分开上报 —— 合并会让界面文案撒谎。

16 医生调整今日任务：覆盖契约

医生可以在患者端「今日任务」上做调整。契约的唯一实现在 src/utils/taskOverride.js，前后端共用，但准入判定在后端 —— 前端无法绕过。

五条红线

  • 规则仍是今日任务的唯一生成者；覆盖层只能改规则已经生成的任务的参数，不得新建规则不存在的任务域（对未生成的任务提交覆盖 → 整包拒绝）。

17 对话提案 → 医生审核联动

患者可以在对话里说「我想把每天的步数目标改成 6000」。系统把它变成一条待审提案，医生审结后才生效 —— 患者端在审结前零变化。

注册用户走同一条提案通道：注册账号只要完成建档，就与示范病例完全一致地提出任务调整。医生端待审列表无论该患者是否已授权，都会显示申请人姓名，并额外标注该患者的授权状态 —— 避免医生面对一条认不出是谁的待审条目。授权与否只决定医生能否查看其档案，不影响提案进入待审列表。

状态机

生成提案（status = pending_review，is_active = 0） │ ├─ 医生「同意」 → approved → 应用覆盖包，患者端即刻生效 ├─ 医生「修改后同意」→ modified → 按医生改后的参数应用 └─ 医生「拒绝」 → rejected → 患者端始终无变化 pending 且生成日期 + 7 天 < 当前时间 → 派生状态 expired

20 系统边界：能做到 / 不能做到

能做到

  • 确定性判定：13 条规则的阈值与命中由代码计算，同一份输入永远得到同一份结果。
  • 可追溯的解释：每条命中都带规则号、依据（basis）、动作建议。
  • 未记录与测得 0 严格区分：缺测不进分子也不进分母。
  • 一次测量一条：事实层纯追加，永不覆盖；作废只打状态位。
  • 等级唯一：晨报 / 落库预警 / 医生端三级同源。
  • AI 参与但不越权：AI 只能提"意见"，不能给分、不能改阈值、不能写库。
  • 医生把关：来自对话的任务调整必须医生审结后才生效。
  • 模型不可用时仍可用：无 Key 自动降级，规则与页面照常。

不能做到 / 不承诺

  • 不是医疗器械：不做诊断，不替代医生判断。
  • 阈值非指南来源：全部是项目内定义的演示规则。
  • 无账号鉴权体系：医生端写接口只校验 doctorId 存在，不校验请求者身份。
  • 无实时推送：全项目无 polling / WebSocket；跨端变更需重新进页面。
  • 跨日预警会重复呈现：alerts 是按「患者 + 规则 + 日」的快照，跨天使用同一账号会看到重复卡片。
  • 勋章运行时不解锁：只有种子数据，新勋章靠 seed 写入。
  • 不做用药建议：药量与方案调整一律指向"联系医生"。
  • 不自动外发通知：紧急联系人通知需用户本人点击确认。

为什么 verify-register-flow 是 22 / 25？（如实说明，不修改测试）

该脚本写于「注册即授权」的旧语义下，其中 3 条断言直接断言旧行为（「医生端随库出现该患者」「患者总数 = 示范 3 + 新注册 1」）。隐私改造后「注册不再等于授权」，这 3 条必然失败；另外该脚本把医生端患者总数硬编码为 4，而库里存在真实注册账号 patient_4「赵小川」。

这是脚本断言与新语义不一致，不是业务逻辑缺陷。未为了让它全绿而修改业务逻辑或放宽断言；待改为「注册后不可见 → 授权后可见」。

为什么 verify-step11-fixes 是 21 / 31？（如实说明，不修改测试）

该脚本这 10 条断言都依赖同一个样本前提：patient_1 在窗口末端应有一个「只录了步数」的缺测日（脚本原注释指向主库 2026-09-15）。该前提来自上一轮修复时的临时数据状态；此后真实库被正常使用填满，演示库的种子数据也是「截至今天的连续 7 天」—— 两个库里都不再有缺测日，脚本找不到样本，10 条断言（1a / 1c / 1d / 3a–3f / 4b）连锁失败。

失败点全部集中在「样本是否存在」，与缺测语义本身的实现无关。修法是让该脚本自造样本（在副本库内把某日的血压 / 血糖置 NULL），属独立一轮的脚本改造；本轮未改动它的任何断言。

为什么 verify-ai-score 有时显示 63 / 63？

该脚本末条断言 Z2（出厂真实库零改动）仅在数据库路径环境变量指向副本库时才注册。不设该变量时自然少一条，得 63 / 63；按基线口径（指向副本库）运行即为 64 / 64。不是回归。
