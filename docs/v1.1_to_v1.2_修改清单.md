## 二、五项修正明细

### 修正 1 · 时序表字段完整性（source / record_status）

**问题**：§8.1 声明「所有时序表必须具备 patient_id + 时间 + source + record_status」，
但 §6 的字段清单里，多数表只列了 `source`，**没有列 `record_status`**；事件表连 `source` 也缺。

**处理**：逐张核对全部时序表，并给出**分类适用边界**（不静默删除铁律）。

- 先修正一处遗漏：**§8.1 表漏了 `doctor_notes`**（§13.2 早已把它标为「时序 = 是」）。
  → 时序表由 **10 张补为 11 张**。
- `source`：**11 张全部必备**。取值 `manual / device / vision / import / agent / rule_engine / system`。
- `record_status`：**分两类**
  - **测量事实型 6 张必须带**：`daily_health_records`、`blood_pressure_readings`、`blood_glucose_readings`、
    `weight_readings`、`lab_results`、`medication_logs`。取值 `draft / valid / corrected / void`（默认 `valid`）。
  - **事件型 5 张不设**：`alerts`、`agent_runs`、`vision_records`、`point_transactions`、`doctor_notes`。
    **理由**：它们只增不改（与 §2.3 铁律 3 一致），更正通过「新增一条并标注替代关系」实现，
    不存在就地草稿/作废工作流；其状态语义由业务列承担（如 `medication_logs.status`、`alerts.confirmed`）。
- **同步落点**：§6 各表字段卡（主干表加 `record_status` 行；4 张细表、medication_logs、alerts/agent_runs/vision_records/doctor_notes/point_transactions 加 `source`）、
  §8.1 铁律表（新增 `source`/`record_status` 两列 + 第 11 行）、§8.1 铁律由「三条」改为「四条」、
  §13.2 增加对照说明。

> 关键澄清：`medication_logs` 的 `status`（依从性：已服/漏服/延迟）**≠** `record_status`（质控：草稿/有效/更正/作废），二者不可互替。

### 修正 2 · 27 张表分类统计的重复计数

**问题**：§13.4 的 C 层（业务数据）清单里**同时列了 `badge_definitions`**，而它又出现在「元数据」行；
导致 C 层实列 **12 个表名却标「11」**，且总和与 27 对不上。

**处理**：
- `badge_definitions` **只计入「元数据」**，从 C 层移除。
- 顺带修正 §13.2 中 `doctor_patient_relations` 的数据层标注：**「B 基础档案」→「C 业务数据」**
  （否则 B 层会变成 7 张，与目标 6 张不符）。
- §13.4 表格重写，新增「合计」行与修正说明。

**三方闭合验证**：

```
分类数量    5（A 健康指标） + 6（B 基础档案） + 11（C 业务数据） + 3（D AI 系统数据） + 2（元数据） = 27
表名清单    各层清单逐张累加 = 27（每张表只出现一次）
§13.2 清单  冻结清单行号 1–27 = 27
```

### 修正 3 · 统一「自动刷新」验收口径

**问题**：§7.3 / §11 / §14 三处表述不一致（「自动刷新」vs「刷新页面后重新读取 API」），
且隐含「实时推送」的过度承诺。

**处理**：全篇统一为：

> **新增数据写入数据库后，重新请求 API 或刷新页面即可看到最新数据；无需修改代码、无需重新构建。**

- §7.3 判据 1 改写；新增「术语统一说明」小节。
- §11.1 闭环描述「结论自动更新」→「结论随之重算」。
- §12.3 标题「趋势图自动更新」→「趋势可更新」，并在流程末补一行「重新请求 API 或刷新页面 → 看到最新曲线与新预警」。
- §14 Step 6、改造前后对照表、验收标准第 3 条，全部改为统一口径。
- 明确：**只有未来真正实现 WebSocket / SSE 时，才称为「实时自动刷新」。**

### 修正 4 · SQLite 表述更正

**问题**：§14 选型表写「换设备查看：随项目文件夹一起拷贝即可」，把本地数据库说成了多端共享。

**处理**：删除该行，改为准确表述，并新增专门说明：

> ① 前端不再依赖 `localStorage` 保存健康数据（localStorage 只保留登录令牌与偏好）；
> ② 健康数据由后端服务访问 SQLite 数据库读写；
> ③ 同一数据库实例上的登录用户，查询到的是同一份数据。

并明确：这解决的是「数据不再锁死在某台电脑的浏览器里」，**不是**「多台设备自动同步」，
即**不是**真正意义上的多端共享数据库。§7.3 判据 2 同步改写。

### 修正 5 · 全文术语一致性复查

**处理**：
- §1 新增**术语约定**表，统一收敛：
  - `patient_id` 为全文唯一患者关联键名；现有代码的 `user_id` 语义相同，第二阶段做一次映射；
    §12.4 冲突 02 因引用现存 schema 而保留原文 `user_id`，并加注说明。
  - `record_date`（日）/ `measured_at`（分）/ `planned_time`·`taken_at`（用药）/ `created_at`（事件发生）
    四类时间字段语义边界写清，特别强调 `created_at` **不是**指标测量时间。
  - `source` / `record_status` 指向 §8.1 铁律。
- 修正 §2.1 / §2.2 中 `doctor_notes` **同时出现在 C 层与 D 层**的矛盾（违背 §2.3 铁律 1「一个字段只属一层」）：
  统一归 **C 业务数据**，D 层描述相应删除「医生审核结果」。
- §2.2 归属映射补上**元数据**一层（`metric_definitions` / `badge_definitions`），使 27 张表张张有归属。
- 补齐 §6 与 §3 的字段差异：`patient_conditions` 补 `diagnosed_at` / `duration_text`；
  `patient_targets` 补 `weight_change_target`。
- §13.3 增加说明：本节「主数据/元数据/时序/事件/业务」是 §6 六层分组，与 §13.4 四层分层是**两套口径**，请勿交叉相加。
- 版本号统一：hero / 目录 / 修订说明 / 交付清单 / 阶段边界 / 页脚 → v1.2。
