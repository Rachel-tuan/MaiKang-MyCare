## 二、必须先拍板的 3 个结构性问题

### 问题 1（最关键）· daily 不写均值，那 `clinicalRules` 吃什么？

这是整份修订要求里唯一的内在矛盾，必须解开。

- 你在**第三节**明确：不要「平均值作为规则唯一输入」，因为会把 `158/146/132` 压成 `145`，丢掉「早晨明显偏高」的信息。
- 你在**第九节**的数据流又写：`写入 *_readings → 必要时更新 daily 汇总 → clinicalRules 重新计算`。

问题在于：**当前 `clinicalRules` 只读 `daily_health_records`，daily 就是它唯一的输入源。** 那么只要规则还读 daily，daily 里那个值就必然是「规则看到的唯一值」——这正是你反对的。

所以只有三条路，**必须选一条**：

| 选项 | 做法 | 是否满足「不丢明细」 | 是否满足「不重写规则」 | 评价 |
|---|---|---|---|---|
| **A（我推荐）** | daily 存**当日峰值**（对血压/血糖这类「越低越好」的指标取当日**最大**值，如 `158/146/132 → 158/96`） | ✅ 明细全在 readings | ✅ 规则零改动 | 峰值是**保守代表值**，不会掩盖异常；医学上评估血压控制本就关注峰值/晨峰，比均值更安全 |
| B | daily 存均值，另给规则加一条「直读 readings」通道 | ✅ | ❌ 要动规则输入层 | 两条路并存，还得定义「一天多条怎么参与连续 N 天判定」，复杂度高 |
| C | daily 不写，规则改读 readings | ✅ | ❌ 大幅改动 | 会直接冲击 step4/5/6 既有验收 |

**推荐 A 的理由**：你要求「不为本功能大规模重写 clinicalRules」，B 和 C 都必然动规则输入层，**只有 A 能同时满足你自己的两条要求**。而且 A 里 daily 存的是峰值（当日最严重值），不是均值，所以**并没有违反你第三节的意图**——均值会掩盖异常，峰值反而放大异常，判定更保守。

> 那句话可以这样冻结：**daily 是「当日保守代表值」层，readings 是「原始事实」层；规则本期读 daily，未来做「日内模式」规则时直接读 readings。**

**请你确认：A / B / C 选哪个。**

### 问题 2 · 「午后」这个时段在数据库里不存在

你第十节要求任务卡显示 `晨起 / 午后 / 睡前`，但 `blood_pressure_readings.slot` 的 CHECK 约束是：

```sql
slot TEXT CHECK (slot IS NULL OR slot IN ('晨起','上午','下午','睡前'))
```

**枚举里没有「午后」，只有「下午」。**（血糖的 `measure_type` 反而完全对得上：`空腹 / 餐后2h / 随机 / 睡前` ✅）

两种解法：

- **推荐**：任务卡**展示**用「午后」，**落库**统一写「下午」，中间做一次映射。零 schema 改动。
- 备选：改 CHECK 约束加入「午后」。但 SQLite 改约束需要重建表 → 属于 schema 变更，与「不新增表/不动结构」的克制原则相悖。

**请确认：用「展示午后、落库下午」的映射方案吗？**

### 问题 3 · 王建军到底该不该出现血糖任务？

你说王建军「不应该机械出现血压/血糖任务」。但我查库发现他的实际疾病谱是：

```
王建军（patient_3）
  主诊断：肥胖症（一级，BMI 31.1）
  合并症：代谢综合征
  合并症：空腹血糖受损     ← 糖尿病前期，不是糖尿病
```

**「空腹血糖受损」在临床上确实会建议监测血糖**，所以直接不给血糖任务，医学上略勉强；但给成糖尿病级的「每日 2–3 次」，又明显过度。

我建议的规则分层（**主诊断决定主任务，合并症只影响低频关注项**）：

| 患者 | 主诊断驱动的主任务 | 合并症带来的附加项 |
|---|---|---|
| 张建国 | 血压监测 2 次（晨起/睡前）+ 服药记录（氨氯地平 08:00） | 超重/中心性肥胖 → 体重记录 |
| 李秀英 | 血糖监测 2 次（空腹/餐后2h）+ 服药记录（二甲双胍 08:00/18:00、阿卡波糖 07:30/12:30/18:30） | 超重/血脂异常 → 体重记录 |
| 王建军 | 体重记录 1 次 + 运动 30 分钟 + 饮食记录 | 空腹血糖受损 → 血糖监测**每周 1 次**（低频关注，非每日）；代谢综合征 → 血压**每周 2 次**（非每日） |

**请确认**：王建军是按上表给「低频关注项」，还是**完全不出现**血糖/血压任务？

## 三、我上一版方案的一处错误（已更正）

上一版方案第四节我写了：

> `medications` 表当前 0 行（未持久化），所以「是否用胰岛素」这类更强指征本期拿不到。

**这是错的。** 实测当前库：

```
medications: 4 行
  patient_1  苯磺酸氨氯地平片  5 mg      每日 1 次   08:00
  patient_2  二甲双胍片        0.5 g     每日 2 次   08:00 / 18:00
  patient_2  阿卡波糖片        50 mg     每日 3 次   07:30 / 12:30 / 18:30
  patient_3  暂无长期用药      —         —          首选生活方式干预
```

**这是个好消息**，它带来三个正面影响：

1. **「服药记录」任务可以直接做**，而且有真实用药计划支撑（张建国 08:00 服氨氯地平 → 与「晨起测压」时段天然对齐，这个演示非常漂亮）。
2. **治疗强度可作为频次依据**：李秀英用两种降糖药（含阿卡波糖每日 3 次）→ 支持更密的血糖监测，有据可依，**不需要 AI 猜**。
3. **王建军的「暂无长期用药」是原样保留的占位行**，正好对应「生活方式干预为主」→ 支撑他走体重管理路线。

同时更正：真正 0 行的是 `medication_logs`（服药打卡明细），所以「服药记录」任务的**打卡写入**是新工作。

> 附带一个实现细节：`medications.time` 是字符串（如 `'08:00 / 18:00'`），而 `medication_logs.planned_time` 是**单个 NOT NULL datetime**。所以做服药打卡时，需要把时段字符串拆成若干计划时刻，一对多展开。

## 四、我在真实库里发现的两个风险

### 风险 1 · patient_1 有一条生理上不可能的数据（建议实施前先处理）

```
patient_1  2026-09-14  →  收缩压 90 / 舒张压 120
```

**收缩压（90）小于舒张压（120），这在生理上不可能**（舒张压不可能高于收缩压）。同时这天的 `weight 76`、`steps 10002` 也与前后 7 天的 `75.0–75.2 / 4800–6800` 明显不连贯，像是测试时误录。

影响：这条数据会污染张建国的血压序列，干扰 `R-BP-2`（血压连续升高）的判定，**演示时若被评委看到会很难解释**。

建议：
1. **加录入校验**（产品改进，你没提但明显该做）：收缩压必须 > 舒张压、数值区间合理性（如收缩压 60–300、舒张压 30–200）。
2. 修正或作废这条历史数据（`record_status` 已有 `void` 枚举，可用状态标记而不是删除——这也符合「不覆盖历史」的精神）。

### 风险 2 · 动态闭环演示会污染主库

你第十三节要求的人工演示（张建国 → 录入 170/105 → alerts 变化 → 医生端可见）会**真实改写主库**。演示一次，`daily`、`readings`、`alerts` 就都变了。

建议：准备一个**演示重置脚本**（恢复到 3 患者 / 21 记录 / 4 预警的初始态），或者演示用独立副本库（`MYCARE_DB_PATH` 指向副本，项目已有这个机制）。否则验收结论不可重复，第二次演示会叠加第一次的痕迹。

## 五、对你「设计原则」的补充建议（3 条）

你的第十五节 5 条原则我都同意，另外补 3 条，请你一并确认：

### 补充 1 · 任务进度不落库，纯派生

你第八节要求「任务与测量记录必须分开」，这非常对。落到实现上，我建议：

> **「2/3 次」这个进度不写进任何表，而是每次实时算：当日 `readings` 条数 vs `target`。**

好处：不新增表、不出现「任务表说 2 次、测量表只有 1 条」的不一致、刷新后天然重现（因为 readings 在库里）。这也让「任务」保持成一个**派生视图**，而不是第二份事实来源。

### 补充 2 · 血糖 `measure_type` 前端强制必选

表结构是 `NOT NULL`。不选就会写失败或语义丢失。建议表单做成下拉、默认「空腹」、不选则前端拦截。

### 补充 3 · 明细的读取通路必须一起补

`patientService.getPatientRecords()` 目前 **只 `SELECT * FROM daily_health_records`，不 join readings**；前端 `normalizeRecord()` 也把明细丢掉。所以任务卡要渲染「✓ 晨起 158/96」，**必须新增读取通路**（`GET /api/patients/:id/readings?date=` 或 records 带 `withDetails`）。这是必做项，不是可选项。
