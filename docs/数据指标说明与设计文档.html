数据关联的三个“锚点”

患者锚点 patient_id
所有数据表的第一关联键。任何一条记录都必须能回答“这是谁的”。当前代码用 user_id，建议统一为 patient_id，并在后端做一次映射兼容。
时间锚点 record_date
所有时序数据表必须有日期字段。当前代码同时存在 record_date（数据库风格）与 date（视图风格）两套命名，靠前端兼容层抹平——这是未来要收敛的重点。
指标锚点 metric_definitions
“新增指标不改页面”的关键：把每个指标的名称 / 单位 / 方向 / 目标 / 适用人群集中声明一处（表或代码常量），页面与 Agent 都从这里读，而不是散落在各处硬编码。

术语约定（v1.2 新增 · 全文统一口径）

术语全文统一用法与现存代码的关系
patient_id 本文件唯一使用的患者关联键名（主键为 patient_id，外键亦为 patient_id） 现有代码使用 user_id 表达同一语义。第二阶段做一次映射（user_id → patient_id），新表一律用 patient_id。
例外：§12.4 冲突 02 在描述「现存代码」时保留原文 user_id，因为它是在引用现有 schema，不是设计方案。
record_date 日粒度时间锚点（DATE）。用于「一天一条代表值」的表，如 daily_health_records、lab_results（后者字段名写作 test_date，同属日粒度） 现有代码另有 date 视图字段，属同一语义，靠兼容层抹平；未来统一收敛为 record_date
measured_at 分钟粒度的「测量时刻」（DATETIME）。用于支持「一天多条」的专项细表，如 blood_pressure_readings / blood_glucose_readings / weight_readings 现存代码无此字段，属新增
planned_time / taken_at medication_logs 专用：计划服药时刻 / 实际服药时刻 现存代码无此字段，属新增
created_at 记录/事件的发生时刻（TIMESTAMP），用于事件型表（alerts / agent_runs / vision_records / point_transactions / doctor_notes）与审计列。

2.3 分层带来的三条铁律

铁律 1 · 一个字段只属一层
不允许同一语义的字段同时出现在两层。例如「HbA1c」只能属于 A 层（lab_results）， 档案层只保留「最近一次检测时间」这种指针，不再保留数值。
铁律 2 · 跨层只用 ID 引用
四层之间不复制数据，只用 patient_id / doctor_id / medication_id 等外键关联。这样「新增患者 = 插一行」才能成立。
铁律 3 · D 层只增不改
预警与 Agent 运行记录是事实留痕，只允许追加、不允许就地修改； 需要更正时新增一条并标注替代关系。
与第 4 章「5 类指标」的关系

第 4 章的 A–E 五类是按指标性质划分（身体测量 / 行为 / 用药 / 派生 / 事件）； 本章的四层是按数据生命周期划分（测量事实 / 慢变属性 / 业务过程 / 系统事件）。 两者是正交维度，互为补充，不冲突。

核心指标详细说明

逐项说明含义 / 单位 / 频率 / 来源 / 页面 / Agent / 规则 / 作用 / 备注

从 26 项指标中挑出 对功能真正起决定作用的 10 项，逐项展开。其余指标（身高、腰围、备注等）语义直观，不重复展开。

收缩压 systolic_pressure
含义：心脏收缩时动脉内的最高压力，高血压管理的核心指标。
单位 / 类型：mmHg / 整数
采集频率：建议早晚各一次；当前演示为每日一次。
数据来源：患者手动录入（未来可接血压计）。
使用页面：首页（今日任务 / 晨报）、健康数据页（趋势图 / 统计卡）、医生端（患者卡片 / 最新数据 / AI 规则）。
使用 Agent：体征分析（趋势统计）、风险预警（分级）、方案规划（目标设定）。
参与规则：R-BP-1 单次超标提示 · R-BP-2 连续异常趋势预警 · R-BP-3 严重超标强预警 · R-BP-4 授权后通知联系人。
作用：驱动血压趋势图、达标率、预警等级；是张建国病例的演示主线。
示例：D7 = 162 mmHg → 命中 R-BP-2（连续 4 天 ≥140 且 7 天涨 +30）；不命中 R-BP-3（162 < 180）。
备注：单次测量不得作为分级诊断依据，只能作为趋势信号。
舒张压 diastolic_pressure
含义：心脏舒张时的最低压力。
单位 / 类型：mmHg / 整数 · 频率：同收缩压 · 来源：患者录入。
页面 / Agent：同收缩压。
参与规则：R-BP-1~4（与收缩压共同判定，任一超标即计入）。
作用：与收缩压成对展示（162/98）；≥110 mmHg 触发 R-BP-3 紧急级。
示例：张建国 D7 = 98 mmHg（未达 110，故不触发紧急）。
备注：必须与收缩压成对存储，不可拆分，否则无法还原“162/98”这一完整读数。
空腹血糖 fasting_glucose
含义：禁食 8 小时以上的血糖值，糖尿病管理的核心指标。
单位 / 类型：mmol/L / 一位小数 · 频率：每日（通常晨起）。
来源：患者自测（血糖仪）或化验单。
页面 / Agent：首页、数据页、医生端 / 体征分析、风险预警、方案规划。
参与规则：R-BG-1 单次超标提示 · R-BG-2 血糖波动提醒（7 天极差 ≥1.4）· R-BG-3 控制不佳趋势（达标率 <60% 且向上）· R-BG-4 复查提醒。
作用：驱动血糖趋势、达标率、饮食处方。
示例：李秀英 7 天 7.1→8.3，极差 1.4，达标率 57.1%（阈值 7.8）→ 命中 R-BG-2 / R-BG-3。
备注：⚠️ 现字段 blood_sugar 未区分空腹 / 餐后 / 随机，但规则判定的是“空腹”，必须新增测量类型字段。
体重 weight
含义：身体质量，用于 BMI、减重进展、代谢风险判定。
单位 / 类型：kg / 一位小数 · 频率：每日（建议同一时间、同一条件测量）。
来源：患者录入 / 体脂秤。
页面 / Agent：首页、数据页、医生端 / 体征分析、方案规划、情感陪伴。
参与规则：R-WT-1 记录达成 · R-WT-2 减重进展（7 天净减 ≥0.5kg）· R-WT-3 短期反弹提醒（单日回升 ≥0.5kg）· R-WT-4 运动达标 · R-WT-5 勋章进度。
作用：驱动减重趋势、BMI、运动目标；是王建军病例的演示主线。
示例：王建军 92.0→90.8（净 −1.2kg），D5→D6 回升 0.6kg 属短期反弹。
备注：⚠️ 体重受水分、糖原、进食与测量时间影响，7 天净变化不能等同于脂肪减少，也不得使用「平台期」。
步数 steps
含义：每日行走步数，反映基础活动量与运动依从性。
单位 / 类型：步 / 整数 · 频率：每日（可穿戴设备自动同步）。
来源：患者手动录入 / 手机计步 / 手环。
页面 / Agent：首页（今日任务 / 徽章）、数据页、勋章页 / 体征分析、情感陪伴。
参与规则：R-WT-4 运动达标激励 · R-WT-5 勋章进度（「健步如飞」平均 8000 步）。
作用：驱动步数目标完成度、运动勋章、正向激励话术。
示例：王建军 D7 = 6400 步；7 天均值约 4600 < 8000 → 「健步如飞」未解锁。
备注：可穿戴设备接入后应标记数据来源（手动 / 设备），便于质控。
运动时长 exercise_minutes
含义：每日主动运动分钟数，用于判定周运动量是否达标。
单位 / 类型：分钟 / 整数 · 频率：每日。
参与规则：R-WT-4（7 天累计 ≥150 分钟达标）。
作用：与步数共同驱动运动达标、运动处方。
示例：王建军 7 天累计 200 分钟 ≥150 → 命中 R-WT-4。
备注：需与「步数」区分：步数是总量，运动时长是主动锻炼时间。
睡眠时长 sleep_hours
含义：每日睡眠小时数，影响血压、血糖与情绪。
单位 / 类型：小时 / 一位小数 · 频率：每日。
参与规则：均 <6 小时触发「睡眠时长不足」关注级风险（体征分析侧）。
作用：与血压 / 体重做关联分析（如“睡眠不足 + 血糖波动”）。
示例：张建国日均约 6 小时，偏低。
备注：王建军生活画像中有「打鼾明显」，建议未来增加睡眠呼吸暂停筛查标记。
心情评分 mood_score
含义：患者当日情绪自评（1 很差 ~ 5 很好）。
单位 / 类型：分 / 1–5 整数 · 频率：每日。
参与规则：目前不参与确定性规则。
作用：供情感陪伴智能体识别情绪趋势；应纳入情绪曲线。
示例：张建国近期 3–4 分波动。
备注：⚠️ 当前采集了但页面未展示、规则未使用，属于“有数据没场景”，建议在数据页补一条情绪曲线。
糖化血红蛋白 hba1c
含义：反映近 2–3 个月平均血糖水平，属长期控制指标。
单位 / 类型：% / 一位小数 · 频率：每 2–3 个月一次（化验）。
来源：医院化验单（可由多模态识别智能体读入）。
参与规则：R-BG-4 复查提醒（距上次检测 >3 个月）。
作用：与 7 天血糖分属两个时间尺度，必须分开展示，不可混为一谈。
示例：李秀英 HbA1c 7.8%（2 个月前检测）。
备注：⚠️ 当前它被放在患者档案的静态字段 medical.hba1c 里，但它本质是随时间变化的化验结果，应迁入时序化验表。
心率 heart_rate
含义：静息心率，用于心血管风险参考。
单位 / 类型：次/分 / 整数 · 频率：每日。
参与规则：≥120 或 ≤45 触发紧急级风险；运动处方中的强度监测参考。

6

二维数据表设计

先评估「一个指标一张表」，再给出推荐方案

6.1 先回答你的问题：一个指标一张表，适合本项目吗？

✓ 这个方向对的地方
1. 采集频率天然不同——血压每天测、HbA1c 两三个月一次，硬塞一张表会大量空值。
2. 一天可能多次测量——血压有早晚两次，宽表一行装不下。
3. 稀疏指标——没有糖尿病的患者，血糖表里就一行都没有，干净。
4. 新增指标零侵入——加一张表即可，不动老表。
5. 单位与类型精确——mmHg 与 mmol/L 各归各表，不会错配。
✗ 但「一刀切全拆」的代价
1. 跨指标分析要 JOIN 到底——本项目现有功能大量是“同一天多个指标一起看”：健康评分同时要步数/血压/血糖/运动；体征分析要做「体重↑ + 血压↑」「睡眠↓ + 血糖波动」的关联。全拆后每次都要拼回宽表。
2. 与现有代码模型背离最大——数据录入表单、趋势图、规则引擎、Agent 工具全部建立在“一条日记录含全部指标”上，全拆意味着改动面最大。
3. “当日快照”概念丢失——患者端要展示“今天的数据”，全拆后要查 N 张表再合并，逻辑与性能都更重。
4. 规则引擎要重写取数层——13 条规则都基于日序列，全拆后要为每条规则写多表聚合。
推荐结论：采用「宽表主干 + 专项细表」的混合模型

日常“每天一个代表值”的指标（步数、睡眠、心情、运动时长，以及血压/血糖/体重的当日代表值） 放进一张 daily_health_records 日快照宽表作为主干；“一天多测 / 低频化验 / 事件型”数据 放进各自的专项细表。

这样既保住了现有全部功能与规则的“按日取数”习惯（改动最小），又满足了稀疏指标、一天多测、 低频化验的真实需求（可扩展）。全窄表方案作为可选升级路径保留（见 6.3）。

「动态数据」的技术定义

把老师的核心要求写成可验收的规则，而不是一句口号

老师说「数据是死的」，指的不是「换一种方式写死」，而是数据必须能被持续追加、被准确检索、并被下游自动消费。 为了让「活的数据」可验收，本节把它拆成六要素与五条判据。

7.1 一条「活的数据」必须具备六要素

要素字段作用示例（张建国）
① 谁的patient_id归属患者，全库关联键patient_1
② 什么时候测的record_date / measured_at时间锚点，决定趋势与排序2026-09-13 / 08:12
③ 哪个指标列名 or metric_key指标锚点，决定单位与判定systolic_pressure
④ 多少value数值本体162
⑤ 从哪来source质控与可信度：手动 / 设备 / 识别 / 导入manual
⑥ 什么状态record_status草稿 / 有效 / 已更正 / 已作废valid
与铁律的关系（v1.2 对齐）

六要素里，⑤ source 与 ⑥ record_status 在 v1.0 里分别是「一个新字段」和「完全没有」。 v1.1 把它们补为通用约定，v1.2 进一步明确适用边界：所有 11 张时序表都必须带 source； 其中「测量事实型」6 张表还必须带 record_status；「事件型」5 张表因只增不改而不设 record_status—— 完整理由与逐表清单见 §8.1 铁律 3。

7.2 追加，不覆盖 —— 同一个人的同一天怎么存

张建国今天重测了一次血压，不能把昨天的记录改成今天的，而是新增一条：

// ✅ 正确：追加
{ patient_id: "patient_1", measured_at: "2026-09-15 08:12", systolic: 158, diastolic: 96, source: "manual", record_status: "valid" }
{ patient_id: "patient_1", measured_at: "2026-09-16 08:05", systolic: 151, diastolic: 92, source: "manual", record_status: "valid" }

// ❌ 错误：把 09-15 的 158 改成 09-16 的 151（历史被抹掉，趋势失真）

// 唯一允许「就地更新」的例外：daily_health_records 的当日代表值
//   规则：UNIQUE(patient_id, record_date) + UPSERT；同一天重复提交视为「更正当日值」
//   每一次真实测量仍然全部进入 blood_pressure_readings，永不丢失

7.3 五条可验收判据

第二阶段验收时，只要下列五条同时成立，「数据是活的」才算达成——这是可以直接演示给老师看的：

#判据验证方式
1追加即可见：新增一条健康记录写入数据库后，重新请求 API 或刷新页面即可看到最新数据；无需修改代码、无需重新构建。录入后刷新页面，曲线末端出现新点
2不依赖浏览器本地存储：健康数据不再保存在 localStorage，改由后端服务访问 SQLite 数据库；同一数据库实例上的登录用户查询到同一份数据。

3新增患者不改代码：只插入患者与数据，登录后即可看到其档案、趋势与智能体结论新增第 4 位患者，前端零改动
4历史可回溯：任意一天的数据都能被准确检索到，不因后续录入而改变查询 7 天前后同一日期，值不变

术语统一说明（v1.2）

本文件不使用「实时自动刷新」来描述当前阶段的能力——当前是「重新请求 API 或刷新页面后可见」。 只有未来真正实现 WebSocket / SSE 主动推送时，才称为「实时自动刷新」。

一句话定义

动态数据 = 以 patient_id 为归属、以时间为序、以六要素为最小单元的可追加事实流； 页面与 Agent 只通过稳定的取数契约消费它，而不是读一份写死的常量。

铁律（四条，建库时逐条核对）

① 任何时序表缺少 patient_id 或时间字段，即视为设计错误，不得进入第二阶段。

② 索引必须建在 (patient_id, 时间字段) 组合上，保证「按患者取最近 N 天」是单索引扫描。

③ source（来源）是全部 11 张时序表的必备列—— 取值为 manual / device / vision / import / agent / rule_engine / system， 用于区分「设备自动上报」与「患者手输」，是质控与可信度的依据。

④ record_status（记录状态）按表类型区分，不是每张表都用，取值 draft / valid / corrected / void（默认 valid）：
　· 测量事实型 6 张（daily_health_records / *_readings / lab_results / medication_logs）必须带—— 因为它记录的是「外部客观测量值」，存在录入口径错误，需要能作废与更正；
　· 事件型 5 张（alerts / agent_runs / vision_records / point_transactions / doctor_notes）不设—— 理由是它们只增不改（见 §2.3 铁律 3），更正只能通过「新增一条并标注替代关系」实现， 不存在就地「草稿 / 作废」的工作流；其状态语义由各自的业务列承担（如 medication_logs.status 的依从性、alerts.confirmed 的确认状态）。
　本条铁律未删除、未失效，只是明确了适用边界；§6 字段定义与本节完全对齐。

心情评分——一天一个整体感受即可。

宽表存的是「当日代表值」（如晨起血压），可由细表聚合生成，不是一个额外事实。

8.3 原始数据 vs 派生数据

这条分界决定了「哪些字段该入库、哪些应该现算」。原则：原始数据必须入库；派生数据不入库或只做缓存，且永不允许被 AI 改写。

数据项类别是否入库可否由他项重算AI 可否改写说明
收缩压 / 舒张压原始入库（宽表 + 细表）否否测量事实
空腹血糖原始入库否否必须带测量类型
体重 · 腰围 · 步数 · 睡眠 · 心情原始入库否否—
HbA1c · 血脂 · 尿微量白蛋白原始入库（lab_results）否否化验事实
年龄派生不单独入库是（由 birth_date）否避免与出生日期不一致
BMI派生不单独入库是（体重 / 身高²）否现算即可
健康评分派生可缓存是（多指标加权）否缓存需带算法版本
达标率 · 趋势斜率 · 连续异常天数派生入库（每次现算）是（由时间序列）否随数据变化而变，存了就会过期

AI 生成的建议文案AI 输出入库（agent_runs / prescriptions）否—是语言产物，不是数值事实
为什么派生数据不落库

达标率、趋势、预警等级都随新增记录而变。如果把它们当字段存起来，就会出现 「数据更新了、派生值还是旧的」的不一致——这恰恰是「死数据」的另一种表现。 正确做法是每次从原始数据现算；只有需要留痕的判定结果（如某次预警）才落库。

9.2 关键设计约定

问题设计约定
不同患者的数据如何保存？所有表带 patient_id 外键；索引建在 (patient_id, record_date) 上。新增患者 = 往 patients 插一行，其余表自动可挂。
不同时间的数据如何保存？时序表按“一行一天/一次”追加，永不覆盖；查询用日期范围过滤。daily_health_records 用 UNIQUE(patient_id, record_date) 保证一天一条，重复录入走 UPSERT。
一天多次测量怎么办？留给专项细表（measured_at 精确到分钟）；宽表存“当日代表值”（如晨起），可由细表聚合生成。
指标单位如何统一？单位固定在字段语义里（如 fasting_glucose 恒为 mmol/L）；化验类因为单位多样，用 lab_results.unit 显式存。
新增患者要不要改页面？不需要。页面从“指定 patient_id 查询”取数，患者是谁由登录态决定，与页面代码解耦。
新增指标要不要改页面？不需要（理想态）。把指标注册到 metric_definitions（名称/单位/方向/目标/适用人群），前端图表与 Agent 都从注册表渲染。
AI Agent 如何读数据？统一走一个 dataProvider：Agent 只声明“我要 patient_id=X 最近 7 天的指标序列”，由数据层拼装返回，Agent 不关心底层是宽表还是多表。
关键：先把“取数接口”抽象出来，换底层不动上层

无论最终选宽表还是窄表，都必须先定义一个稳定的取数契约，例如 getSeries(patientId, metricKey, days) 与 getDailySnapshot(patientId, date)。 页面与 Agent 只依赖这个契约。这样即使中途从宽表换成窄表，上层代码一行都不用改—— 这才是“活的数据”的真正含义。

12.4 现存数据结构冲突清单（★ 需你决策，我不擅自修改）

以下是代码里已经存在的不一致或口径问题，会影响第二阶段建表。列出供你确认，本阶段不做任何修改。

冲突 01血糖字段语义模糊：只存一个值，未区分「空腹 / 餐后 / 随机」
字段 blood_sugar 只存单个数值，但 R-BG 规则判定的是空腹血糖，李秀英阈值 7.8 也是空腹阈值。若不区分测量类型，未来餐后血糖写入会直接污染空腹趋势与达标率。
建议：宽表字段改名 fasting_glucose；新增 blood_glucose_readings.measure_type 承载餐后 / 随机。
冲突 02血压一天只能存一次（UNIQUE user_id + record_date）
现有 health_records 表对 (user_id, record_date) 建了唯一键，一天只能一条。但真实血压管理需要早晚各一次，且复测很常见。当前无法表达。
（此处 user_id 是现存表的字段名，语义等同本文档统一使用的 patient_id，见 §1 术语约定。）
建议：宽表保留当日代表值，新增 blood_pressure_readings 细表存每次测量。
冲突 03HbA1c 被放在患者档案里，但它本质是随时间变化的化验结果
medical.hba1c = 7.8 是静态字段，而 HbA1c 每 2–3 个月复查一次、会变化、需要历史对比。放在档案里等于「只存最新一次、且与档案更新耦合」。
建议：迁入 lab_results 时序表；档案只保留「最近一次检测时间」用于 R-BG-4 判断。
冲突 04智能体的预警 / 提醒 / 运行记录全部不落库
「自主触发 N 条预警」刷新页面就消失；医生端看不到患者被触发过什么预警；协同过程无法回放。这与「活的数据」目标直接冲突。
建议：新增 alerts / reminders / agent_runs 三张事件表。
冲突 05医生备注是组件内写死，且未与医生表关联
DoctorPage 的 doctorNotes 用 useState 初始化两条假数据；doctor_id 未与 doctors 表建立外键关系。刷新即回到初始值。
建议：落 doctor_notes 表，doctor_id 外键指向 doctors。
冲突 06生活画像的「职业」字段位置不一致
后端 tools.js 的 get_user_profile 读取的是 user.lifestyle.occupation， 但 demoPatients.js 把职业放在 profile.occupation，lifestyle 里并没有该字段。 结果是 AI 拿到的「职业状态」永远是 undefined。
建议：在 patient_lifestyle 里补上 occupation，或统一由 patients 表提供。
冲突 07疾病表达存在「中文病名」与「英文枚举」两套并存
demoPatients / 医生端用中文规范病名（原发性高血压、2 型糖尿病）， 而 ProfilePage / PrescriptionPage 的表单用英文枚举（hypertension、diabetes）。中间靠 disease.js 关键字匹配兜底。
建议：统一以中文规范病名为存储值，英文枚举只在表单内部作映射。
冲突 08注册用户与示范病例的结构不一致，会导致 AI / 规则降级
UserContext.buildRegisteredProfile() 生成的注册用户没有 lifestyle / medical / medications / 结构化 emergencyContact。 这类用户登录后，个性化建议（依赖 lifestyle）、控制目标（依赖 medical.demoThreshold）都会走默认值或空值。
建议：patients 表把这些列全部标准化为可空列，注册流程补一个「完善档案」步骤。
冲突 09勋章类型存在三套枚举 / 命名
schema.sql ENUM：步数达标 / 连续记录 / 体重下降…
demoPatients：初次记录 / 连续记录
BadgePage 目录 id：first_record / week_streak / steps_10k…
建议：建 badge_definitions 目录表统一 id 与显示名，勋章记录只引用 id。
冲突 10采集了但没用的数据（mood_score / notes / sleep_hours 部分）
mood_score 已采集但页面无任何情绪展示、规则不使用；notes 字段全程无展示；sleep_hours 只在体征分析里做过一次均值判断。
建议：要么补上对应场景（情绪曲线、备注展示），要么明确标注为「预留字段」，避免被质疑数据冗余。
冲突 11积分只有累计值，没有流水
localStorage.userPoints 只存一个数字，无法回答「这些分是怎么来的」，规则 R-WT-1 说「积分 +10」但没有任何账目记录。
建议：新增 point_transactions 流水表，累计值由流水求和得出。

v1.2 更正：SQLite 的「可见范围」到底是什么意思

不要把「拷贝项目文件夹」描述成多端共享数据库。准确的机制是：

① 前端不再依赖 localStorage 保存健康数据（localStorage 只保留登录令牌与偏好设置）；
② 健康数据由后端服务访问 SQLite 数据库读写；
③ 因此同一个数据库实例上的登录用户，查询到的是同一份数据。

也就是说，它解决的是「数据不再锁死在某一台电脑的浏览器里」，而不是 「多台设备之间自动同步」。真正意义上的多端共享，需要在同一台后端服务上访问同一个数据库文件—— 这一点在本地演示场景已经完全够用，答辩时也能直接打开 .db 文件展示。

结论

采用 SQLite（Node 侧用 better-sqlite3 或 sqlite3）。 老师真正想看到的不是「你用了 PostgreSQL」，而是「你这个数据真的不是写死的」—— SQLite 完全能证明这一点，且演示风险最低。若后续确需迁移，第 6 章的表结构为标准 SQL，改动集中在数据访问层。
